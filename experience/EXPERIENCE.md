# EXPERIENCE — operational facts earned by running astropathica

Descriptive, dated, public-safe. What the code taught us by running, not by reading.

- **readpst preserves the read flag** as a `Status: RO` header on read messages (absent on unread); `2-parse.py` maps it to `is_read`. Verified on a 5,358-message Inbox: 1,298 unread. (observed 2026-08-21)
- **Outlook's export wizard exports only what the local cache holds.** Exporting the mailbox root while Outlook Classic was still syncing produced a PST with Inbox but no Sent Items (the folder showed no item count in the dialog). Wait for counts next to every folder before exporting. (2026-08-21)
- **Some Italian mail servers localize the Date header** (`Sab, 22 Ago 2026 …`), which `email.utils.parsedate_to_datetime` rejects; without the fallback ~1% of messages had no date. (2026-08-21)
- **A sender/keyword filter cannot separate commitments from reference in an academic inbox.** Four mechanical rules (To-me, known senders, deadline words, threads replied in) flagged 73% of 1,298 unread and still left ~20% live items in the "safe" pile (sampled 40). The distinction is in the body; only a reader gets it. (2026-08-21)
- **Triage pass cost is dominated by the cached context, not the emails.** With a ~146k-token system prompt (the vault state) cached, a 25-email call on Opus 5 via OpenRouter costs ~$0.30 ($0.35 first measured) and ~65 s; the same on DeepSeek V4 Pro ~$0.027 and ~150 s. Every edit to the system prompt invalidates the cache: one extra ~$1.15 write on Opus. Freeze the prompt before a long run. (2026-08-21)
- **DeepSeek V4 Pro writes longer JSON than Opus** and truncated a 25-email batch at an 8k output cap; raised to 16k and added salvage of complete objects from a truncated array. (2026-08-21)
- **Opus 5 vs DeepSeek V4 Pro on the same 50 emails:** 42/50 verdict agreement, 37/50 tag agreement. DeepSeek caught one already-captured action Opus missed; DeepSeek marked five self-notes "likely resolved" without evidence (the expensive error direction for a review queue). (2026-08-21)
- **Outlook keeps the exported PST open after the export dialog disappears, and neither size nor mtime tells you it is done.** On a 2.29 GB export the size plateaued at 15:09, the progress window was already gone, and the mtime still advanced to 15:12. Afterwards the file stayed unreadable — from WSL as `Input/output error`, from PowerShell as `IOException` — as a *byte-range lock on the header only* (offsets 1 MB and 1 GB read fine, offset 0 did not). The PST was not listed under Account Settings → Data Files. Only exiting Outlook released it. Rule: export, then quit Outlook, then copy. (2026-08-23)
- **The export wizard's date filter parses MM/DD regardless of the Windows locale.** "31/05" is not a valid US date, so the filter was silently dropped and a "May–present" export came out as the whole Inbox (Jan → today, 5,405 messages) plus every other folder. Written as `07/31` the same wizard produced exactly Jul 31 → today (521 messages, Sent Items included). Always check the parsed date range, not the file name. The May run also had 3 of 5,405 Inbox messages fail in `2-parse.py` with `list index out of range` (not yet diagnosed). (2026-08-23)
- **Targeted project lookup needs no index.** A regex over subject+body of the 7,268-message JSONL isolated the 35 emails of one proposal in seconds; the loose first pass (a coordinator's surname) hit 257 because she is cc'd on half the department — filter on the project name and the thread subjects, not on people. Attachments were recoverable directly from the readpst mbox with `mailbox` + `get_payload(decode=True)` — no Phase 4 needed for a handful of files. (2026-08-23)
- **A random sample of 50 *read* emails contained 4 LLM-flagged actions (8%)**, of which the owner judged 3 as handled off-system — ~1/50 real. "Read" ≈ handled in this mailbox. (2026-08-21)
- **Full backlog triage, measured:** 3,516 unread Inbox emails (2022–2026) in 124 calls of ≤30 emails, thread-packed, Opus 5 via OpenRouter, 91k-token cached system prompt: **2 h 05 min, $42.96** — 23.0M input tokens of which 85% cache hits, 640k output. Verdicts: REFERENCE 81%, NOISE 12%, ACTION 6.2%, WAITING 0.3% — the review queue is ~1/16 of the pile. 23 emails (0.7%) came back without a verdict (model skipped ids in long batches; one batch truncated and was salvaged); the resumable re-run fixed them in one call, but at **$1.25 uncached** because the 5-minute cache had expired overnight — resume immediately after a run, not the next morning. (observed 2026-08-25)
- **A 30-email batch with a 91k prompt costs ~$0.35 with cache hits and ~$1.25 without.** Whole-run cache-hit rate 85%: the first call of each run and the occasional retry miss it. (2026-08-25)
- **Reviewing a 231-line LLM triage queue took three human sessions (~6 h total, ~40 rows/hour) — 3× the machine pass that produced it.** The bottleneck is not reading but *routing*: each kept row becomes a dated action, a tickler, a delegation or a filed attachment, and the owner must decide which. What sped it up: month-sized batches printed with the date column (the reviewer hunts the email on a second screen by date), a one-line suggested fate per row that the owner overrides inline, and executing the whole batch in a single scripted write. Keep ratio measured on the last 129 rows: ~55% kept, 45% dropped — the LLM's ACTION verdict is a candidate list, not a decision. Row numbers in a combined table (e.g. "106+107") are a trap for spoken rulings: the reviewer counts rows, not ids — number every row by email id only. (observed 2026-08-29)
- **Message-ID dedup across overlapping PST exports is exact.** Merging the full-mailbox export (49,412) with three later overlapping partial exports (3,854 / 124 / 1,588 messages) added 710 + 0 + 762 new records; the one export fully inside another's window contributed zero. Overlap is free, so the delta export can start a couple of weeks before the previous end date with no cost. The merge of ~55k records runs in seconds, stdlib only. (observed 2026-10-16)
- **A typed date in the export wizard's Advanced filter (`Received` → `on or after` → `09/28`) produced an empty PST: 271,360 bytes, the full folder tree, zero messages.** The same wizard with the relative condition `Received: this month` (no value typed) produced 183 MB / 749 messages for Oct 1–16, Sent Items included. The owner's reading, after a repeat: the typed-date condition is what fails, not the timing of quitting Outlook (an earlier hypothesis). This matches the August finding that typed dates are fragile (`31/05` was silently dropped and exported everything). Rule: use the relative conditions (`this month`, `last month`, `anytime`) and never type a date; a PST near 265 KB is an empty shell, re-export before converting. (observed 2026-10-16)
- **A fresh full export vs the stitched corpus (full + 4 deltas, same day): 51,197 vs 51,627 records.** The 512 present only in the stitched one were 488 Junk Email (Outlook auto-purges junk after ~30 days, so delta exports keep spam the mailbox has already dropped), 15 Drafts since discarded or sent, and 9 Inbox items the owner had deleted (all newsletters, review invitations, spam). The 82 present only in the fresh dump were mail of the last day. No substantive email differed, so a periodic clean full export is a safe way to reset the corpus; the stitched corpus is the one that over-remembers. The 20.3 GB PST converted in ~15 min and parsed in ~25 min; 23 of 51,220 messages (0.05 %) still fail with `list index out of range`, undiagnosed since August. (observed 2026-10-17)
- **WSL2's page cache does not give memory back after a big file job.** Converting a 20 GB PST with readpst (20 GB read, 19 GB written) left the WSL VM holding ~10 GB of host RAM after the process had exited; Windows cannot reclaim it without `autoMemoryReclaim` in `.wslconfig` or a `wsl --shutdown`. Windows' own file cache is standby memory and is reclaimed on demand. Rule: read-heavy jobs on the mailbox run on native Windows, or cap WSL in `.wslconfig` first. (observed 2026-10-18)
- **Outlook Classic in cached mode can stop syncing the Calendar folder silently while mail stays current.** No Sync Issues entries, no error; the tell is the newest `CreationTime` in the folder (3 months old on a machine receiving mail daily). The fix is Calendar → Properties → Clear Offline Items → Send/Receive. A calendar exported from such a profile is stale without any warning in the PST; export from the machine whose calendar is current, or check the newest event date before trusting it. (observed 2026-10-18)
- **libpff reads a 20 GB PST directly, on Windows, with no intermediate files and no failures.** `2-parse-pst.py` (libpff-python 20260926, Python 3.12, PST on a Dropbox-synced NTFS drive) produced 52,682 records from the same export that readpst + `2-parse.py` had turned into 51,197 (+1,485: readpst drops part of the meeting-request/response traffic, and the 23 `list index out of range` mbox failures do not exist on this path). Open ≈ 13 s; walk 24.5 min at 35–95 messages/s (slower on folders with big HTML bodies and attachment tables) → 168 MB JSONL; 368 Message-ID duplicates across folders dropped; 0 errors. API notes that cost time: `record_entry.data_as_string` etc. are properties, not methods; `message.html_body` raises `OSError` when the property exists but is empty — read the raw entry (`0x1013`) instead; `recipients.get_record_set(i)` returns record sets directly; unicode properties are UTF-16-LE bytes; HTML bodies are raw bytes in the message's `PR_INTERNET_CPID` codepage, which is often declared ascii while carrying UTF-8 — decode strict with the declared codepage, then UTF-8, then cp1252 lossy (84 of 52,682 bodies kept a replacement character). Sent Items carry no transport headers; Message-ID / In-Reply-To / References come from the MAPI properties (`0x1035/0x1042/0x1039`), present on every item but 3. (observed 2026-10-18)
